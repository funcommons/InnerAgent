## 3. 场景明细

### 3.1 steady-30min ×2(100 并发)+ 25VU 判别

**A. 纯回复形态**(`043002Z`,上午;6→3 事件/运行,347k→268k 事件):
89,442 运行零失败;透传 P95 286ms;首字 1,643ms;详细分布见 git 历史(首轮版报告)。

**B. 工具流形态**(`073013Z`,下午;6 事件/运行 —— 与 ramp 校准一致):

| 指标(ms) | avg | med | p90 | p95 | max |
| --- | --- | --- | --- | --- | --- |
| 首 CONTENT(全含) | 2,045 | 1,849 | 2,907 | **3,375** | 18,074 |
| 透传 | 482 | 358 | 965 | **1,227** | 11,055 |
| 事件间隔 | 442 | 394 | 773 | 851 | 6,248 |
| 运行时长 | 3,271 | 3,106 | 4,189 | 4,617 | 22,942 |

57,838 运行零失败,175 events/s,事件/运行恒定 6.0。

> **注(首字越线归因)**:工具流 = 两次模型调用(mock 二段出字)+ 下午机况更重,
> 两因素叠加使全含口径 P95 3,375ms > 3s 线。同机判别实验(25VU)同形态首字 P95
> 923ms —— 专机复测预计大幅回落;此线在专机复测中重判。

**C. 25VU 判别实验**(`065953Z`,纯回复形态):3,034 运行零失败;透传 med 9 /
p95 60 / max 136ms;首字 P95 923ms。
**对照结论:透传延迟随负载线性增长(事件率 ×3.4 → P95 ×4.8),无积压放大 ——
单机共存 CPU 争抢主导,服务端透传路径(SSE 直发,不经 outbox)健康。**

- fan-out 健康位(各轮 after-prometheus):`event_backpressure_rejected` /
  `harness_capacity_rejected` / `state_bulkhead_rejected` **全 0**;GC 均值
  3.2ms/次,无 Full GC。

### 3.2 idle-sessions(1000 空闲会话)—— 验收 7 核心场景

- 形态:SSE 半开(ALWAYS_ASK → `get_current_time` → WAITING_CONFIRMATION,
  24h 确认超时挂起);节奏 3m 爬坡 + 10m 保持
- **建立+驻留:通过** —— `空闲会话建立` check 1000/1000;服务端 `runs_waiting`
  2 → **1002** 全程驻留,压测结束后 30min+ 活体探针仍 1002(确认卡挂起语义正确)
- **内存:不通过(O-3,真发现)**,证据链:
  1. 驻留期 heap 2.92 → 6.92GB(`ia_idle_heap_used_bytes` min/max,52 样本);
  2. 压测结束、**零流量、1002 会话仍驻留**条件下活体复测:老年代
     **7.226 → 7.421 GiB / 90s = +86MB/min**(eden 3.5GB 为未清垃圾不计入判定);
  3. 外推:~5GB/h @1000 会话 ≈ 86KB/min/会话,默认堆(48GB 机 1/4=12GB)数小时 OOM
- **采样器缺陷(已修,不影响上述服务端证据)**:k6 `constant-vus` 在 exec 于内部
  deadline 返回后重迭代空转(3.38M 个 0ms 幻迭代污染 iterations 指标);
  修复 = deadline 后睡到场景结束(`9a0cee3` 后续提交)
- 排查方向(平台侧):确认超时调度器对挂起运行的周期性扫描/重分配;挂起运行的
  Reactor 订阅链/唤醒提示保留;`WAITING_CONFIRMATION` 状态的 journal 快照重读

### 3.3 ramp-events(500 events/s)

- 到达 2m → 83 运行/s(=500÷6 校准)× 10m → 1m;VU 池 623
- **1m02s 处 abortOnFail 熔断**(checks/failed_rate/passthrough 三阈值):623 VU

  工作(1 分钟内止损)
- 价值:熔断数据 + steady/idle 数据共同框定「本机形态上限 ≈175 ev/s / 100 并发」,

## 5. Redis 与关键发现

Redis(`baseline` vs `steady-after`):used 1.25M 恒定,峰值 7.06→8.60MB,
clients 2,rejected 0,noeviction 未触淘汰 —— **水位无虞**。

### O-1:outbox 消化能力低于设计点 → **已批量化修复(当日,合并 `24d6609`)**

实测背景:backlog 基线 303,200 → steady 后 415,392(净增 112k ≈ 入流 135 ev/s −
消化 60-80 行/s);停载后 ~2h 排空;25VU 期间 backlog≈6。机理:
`AgentEventOutboxScheduler` 500ms×200 行批,逐条 publishOne。

**修复**(`f51076e`,worktree 合入):认领 `UPDATE ... IN` 单语句批量 + Redis 唤醒
`flatMap(128)` 有界并行(Lettuce 同连接 pipeline)+ 批量 ack(行数不足回退逐条),
失败隔离/退避/脱敏/租约语义不变。批内往返 604 次 → ≈8 次(~75×),预期对齐
**~400 行/s 设计点**(500ms×200 行;再上调需动 `outbox-delay-ms`/BATCH_SIZE)。
验证:surefire 889/889(叠加 O-3 后);testcontainers IT 双节点互斥认领/租约接管/
重复唤醒幂等/毒丸退避 5/5;**设计点实测数字待下轮压测回填**。

### O-3:挂起(WAITING_CONFIRMATION)会话内存持续增长 → **双层根因已修(当日,`775c25d`)**

实测背景:老年代零流量 +86MB/min @1002 驻留(7.23→7.42GiB/90s;后段加速至
~110MB/min),外推 ~5GB/h。

**根因(两层,均活体实锤)**:
1. `AgentRunReplayService` 回放/活尾循环以 `flatMapMany` 内联递归订阅下一轮
   (300ms/轮,挂起运行永不终止)—— Reactor「活跃叶子保住整条祖先链」,每轮的
   MonoDelay/门 lambda 全部滞留(修复前堆内 237,115 个 MonoDelay 同时存活);
2. `AiPipelineController` 半开 SSE 跑在 Servlet 容器上取消是惰性的 —— 挂起运行
   无事件可写,客户端断开容器永不察觉,循环空转 MySQL 永不释放(200 条 CLOSED
   连接 + 200 条 Redis 订阅 70 分钟不释放)。

**修复**:循环改 `Flux.defer(cycle).repeat().takeUntilOther(finished)` 扁平结构
(每轮全新订阅、完成即整链释放);三条 SSE 端点包 `withKeepAlive()`(30s 注释行
暴露死连接 → 写失败 → 流+循环+订阅一并释放)。

**修复前后同口径对比(200 会话,零流量)**:

| | 修复前 | 修复后 |
| --- | --- | --- |
| 老年代斜率 | **+37.8MB/min** | **+0.12MB/min(噪声)** |
| 堆内 MonoDelay/门 lambda | 237,115×3 | 0 |
| Redis pub/sub 残留连接 | 200 | 0(~90s 内释放) |
| 空转 MySQL 轮询 | 200×3.3qps | 0 |

验证:surefire 883/883(该提交时点;叠加 O-1 后 889/889);demo 回归 24/24。
**验收 7 内存关待下轮压测正式复勾**(机制已修,预期达标)。
