## DEF-02(UI「刷新」空体分诊破坏指纹一致性)· P1

- **现象**:ToolsView「刷新」按钮按设计「不重发 schema、按现库分诊」(视图注释),实际实现是 `POST /tools/{id}/schema` **空 body**。服务端把「空 schema vs 现库 schema」判为 compatible(`nested_schema_changed`),并进入 COMPATIBLE 分支:
  1. 响应 `effectiveSchemaSha256` = **空串的 SHA-256**(e3b0c442…),与库内真实 schema 脱节;
  2. `schema_sha256` 列被 updateById 持久化为空串指纹(`parameters_schema` 因 MyBatis-Plus 空值跳过更新而幸存)→ **内容与指纹脱节落库**;
  3. `ia_tool_schema_history` 新增 `compatible/applied` 失真行;授权快照指纹基准失真;
  4. 后续以指纹为基准的分诊、内核快照(ADR-5)与授权级联判断全部被污染。任何管理员点一次「刷新」即触发。
- **证据**:`assets/L3-05b-DEF02-空体分诊-响应.json`(verdict=compatible,effective=e3b0c442…)、`L3-05b-DEF02-刷新后工具实态.json`(parametersSchema 非空 + schemaSha256=空串指纹)、`L3-05b-DEF02-结论.txt`。
- **修复意见**(二选一,推荐 ①):
  1. 服务端:`refreshSchema` 的 `nextSchemaJson` 为空/缺省时视为「不重发」,直接走 UNCHANGED 静默刷新(与视图注释语义对齐);COMPATIBLE/BREAKING 分支仅在 `nextCanonical` 非空时才覆写指纹,空值绝不落 `schema_sha256`;
  2. web 端:「刷新」按钮先 GET 当前 schema 再原样回发,或移除该按钮(活刷新应由宿主 `tools/list_changed` 驱动);
  3. 数据修复:对已被写坏的工具(`schema_sha256` = e3b0c442… 且 `parameters_schema` 非空)按现库内容重算指纹回填,并清理对应失真 history 行。
- **定级理由**:管理面单键触发、静默发生、污染「指纹即事实」的分诊与快照链路,违反 ADR-5 的可复现性初衷。

## 发现项(不定缺陷级)

- **schema 历史 UI 无入口**(FIND-P3):store 已有 `schemaHistory` action,视图未挂任何入口,历史只能在 API/库层查看(本线用例 11 即 API 取证)。修复意见:工具行操作列加「历史」抽屉。
