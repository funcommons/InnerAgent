## 1. 已实测的容量事实(基线口径)

| 维度 | 实测 | 条件 |
| --- | --- | --- |
| 并发运行 | **100 并发 × 30min,89,442 运行零失败**,拒绝位(backpressure/capacity/bulkhead)全 0 | 15 核 Mac,JVM+DB+负载机共存 |
| 首字延迟 | P95 1,643ms(全含,canned mock) | 同上 |
| 事件透传 | P95 60ms @25 并发 ✅;286ms @100 并发(共存争抢,判别实验定性为环境受限) | 专机复测定稿 |
| 库容量消耗 | **≈18KB/运行**;journal ≈10 事件/运行;SSE 投影 3 事件/运行 | steady 33min |
| 空闲会话 | 1000 个 SSE 半开会话建立与保持正常(idle 场景) | 见报告 §3.2 |

**容量承诺(有条件)**:按 18KB/运行与 10 journal 事件/运行折算 ——
1 万 DAU × 人均 20 轮/天 ≈ 20 万运行/天 ≈ 3.6GB/天库增量,**生产必须配
journal 归档/分区策略**。

## 2. 容量规划三步法

1. **估运行画像**:日均运行数、并发峰值(高峰小时运行数/3600 × 平均运行时长
   ~2-3s)、每轮工具调用数;
2. **对表上节基线**:并发对 100(专机余量更大),库增量对 18KB/运行;
3. **留两处专项余量**:outbox(§4)与模型供应商限流(`max_concurrency` 排队)。

## 4. 已知容量边界:outbox 消化能力(O-1)

**事实**:outbox(跨实例 SSE 唤醒桥)当前调度为 500ms × 200 行/批,逐条发布;
实测消化 ~60-80 行/s,低于 500 ev/s 设计点。单实例部署的 SSE 直发**不受影响**
(不经 outbox);影响的是**多实例部署下的跨实例唤醒/重连时效**与持续高吞吐下的
积压水位(实测 400k 积压可在停载后 ~2h 排空)。

**规划口径**:

- 单实例/中低吞吐:不用管,`outbox_backlog` 仅作观察位;
- 多实例/高吞吐:升级排程配置(`outbox-delay-ms` 调小 + 批量发布,平台待办已
  登记)并给 `outbox_backlog` 配告警(如 >5 万持续 10min)。

## 5. 压测怎么做(复用本仓工具)

```bash
# 环境:server :18090 + mock 模型为默认(见 03-接入指南/05)
PATH="$HOME/go/bin:$PATH" SCENARIOS="steady,idle,ramp" KEEP=1 \
  IA_EVENTS_PER_RUN_ESTIMATE=3 tools/k6/run.sh
```

- 四场景:smoke(门禁)/ steady(并发稳态)/ idle(空闲会话内存)/ ramp(吞吐爬坡);
- 阈值 = 验收原文,`IA_THRESHOLD_*` 可覆盖;`KEEP=1` 保留环境(默认 teardown
  会连 compose 一起下掉,**共享演示库时必须 KEEP=1**);
- 结果:`tools/k6/results/<UTCstamp>/`,按 `capacity-report-TEMPLATE.md` 回填。

**三个实录教训**:

1. mock `deltaMs` 决定事件率(60 → ~3× 事件率),压测前后口径必须一致并在报告记录;
2. 负载机与服务端**同机会把尾部延迟放大数倍**(判别实验:透传 P95 60ms@25VU vs
   286ms@100VU 同机)—— 正式容量结论必须负载机分离;
3. `IA_EVENTS_PER_RUN_ESTIMATE` 按实测校准(canned 默认回复 ≈3 事件/运行),
   否则到达率折算失真。
