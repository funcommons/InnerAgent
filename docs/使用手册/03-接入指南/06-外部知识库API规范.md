# 接入指南 · 06 外部知识库 API 规范

> 适用:宿主已有检索/知识系统(内部 wiki、业务搜索、RAG 服务等),希望助手回答时
> 引用其中内容。方向:**平台发起检索,宿主返回命中**——宿主只需实现一个 HTTP 检索
> 端点,并在管理面登记。
>
> 注:管理面端点为规划路径,实现以管理面实际为准。

## 1. 定位与运行行为

| 关注点 | 口径 |
| --- | --- |
| 与内置 mini KB 关系 | 并存:每次运行两路同时检索,命中清单 RRF 融合后注入(与内置语义层共用同一融合语义) |
| 引用注入 | 融合命中以「引用资料」区块进上下文,防注入包裹与本地 KB 完全同源 |
| 失败降级 | 外接源不可用**不阻断会话**:按该源零命中继续,平台侧 WARN + 指标计数 |
| 引用溯源 | 命中的 title/anchor 原样出现在对话引用块来源与运行引用留痕 |

## 2. 登记契约(管理面 · 应用级)

形态对齐三方 MCP 应用级注册([04-MCP 三方工具接入](04-MCP三方工具接入.md)):由平台管理员
(`X-IA-Admin-Key`)登记,对应用内所有用户生效;凭证只存管理面,永不出现在审计日志;
管理面属可信配置,允许内网端点。

| 字段 | 说明 |
| --- | --- |
| `endpointUrl` | 宿主检索端点(POST) |
| `authType` | `NONE` / `STATIC_HEADER` |
| `headerName` + `credentials` | `STATIC_HEADER` 时成对必填(如 `Authorization` + `Bearer ...`) |
| `timeoutSeconds` | 单次检索超时,默认 10 |
| `enabled` | 启停开关 |

管理面将提供(与 `/ia/api/v1/admin/kb/documents` 并列,路径以实际为准):

| 端点 | 用途 |
| --- | --- |
| `POST/GET/PUT/DELETE /ia/api/v1/admin/kb/external` | 登记/列表/编辑/删除(每应用暂限 1 个) |
| `GET /ia/api/v1/admin/kb/external/search?appId=&query=` | 检索调试:直接看宿主返回与融合结果 |

## 3. 检索请求(平台 → 宿主)

`POST {endpointUrl}`,请求头:

| 头 | 说明 |
| --- | --- |
| 登记的静态头 | 如 `Authorization: Bearer ...`(`authType=NONE` 时无) |
| `Content-Type` | `application/json` |
| `X-IA-Signature` / `X-IA-Timestamp` | **可选,默认关**。开启后为 HMAC-SHA256 签名(hex 小写,覆盖时间戳与请求体),密钥复用 Webhook 侧密钥机制,宿主可据此确认请求确由平台发出;签名串格式以管理面实际为准 |

请求体:

```json
{
  "query": "用户可见消息文本(平台已安全过滤)",
  "topK": 4,
  "appId": 1
}
```

- `query`:本次运行的用户消息文本。平台已过滤,宿主仍应按不可信输入对待;
- `topK`:建议返回条数,默认 4,平台侧钳制 ≤50;
- `appId`:发起会话的应用 id(宿主单端点多应用分流用)。

超时默认 10s(可配);**失败不重试**——会话时效优先,失败即按该源零命中。

## 4. 响应契约(宿主 → 平台)

`200` + JSON:

```json
{
  "hits": [
    {
      "title": "文档标题",
      "anchor": "章节/锚点,可空",
      "content": "分段正文(必填)",
      "score": 0.87
    }
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | 建议 | 文档标题,原样出现在引用块来源 |
| `anchor` | 否 | 章节/锚点;给出时来源展示为「title §anchor」 |
| `content` | **是** | 分段正文;超过平台配置上限会被截断 |
| `score` | 否 | 浮点,仅排序参考 |

降级规则——**任何非 200 / 超时 / 畸形 JSON / 响应体超上限(建议宿主自限 ≤1MB)一律按
该源零命中处理**,平台 WARN + 指标计数,不重试。命中条数超过 `topK` 时平台按序取前
`topK` 条,多余丢弃(不算错误)。

## 5. 宿主接入四步

**① 实现端点**——先本地自测(模拟一次平台请求):

```bash
curl -X POST https://wiki.example.com/ia-kb/search \
  -H "Authorization: Bearer $WIKI_TOKEN" -H "Content-Type: application/json" \
  -d '{"query":"报销流程","topK":4,"appId":1}'
```

**② 登记**:管理面填 endpointUrl + 鉴权头,启用(或走 §2 的 CRUD 端点)。

**③ 调试**:`GET /ia/api/v1/admin/kb/external/search` 直接看命中与融合结果。

**④ 观察**:发起对话,确认回答带 `[KB:分段id]` 溯源标注、前端引用块来源正确。

### 安全边界

- 引用块由平台以 `<kb_reference>` 标记包裹并过滤,宿主**不需要做转义**;
- title/anchor **不应包含伪造的引用标记**(如 `<kb_reference>` 字样):平台已过滤,
  但宿主返回干净字段可让引用展示更可靠;
- `content` 是资料不是指令:平台侧声明其不得覆盖系统提示词,宿主无需也无法改变这一语义。

## 6. 限制与配额

| 项 | 值 |
| --- | --- |
| 融合后注入预算 | 8000 字符/次运行,与本地 KB 共享(按命中顺序累计,超预算整段截停) |
| 工具配额 | 外接源是知识源不是工具,**不计入**每用户 32 工具配额 |
| 每应用外接源数 | 暂限 1 个,后续按需放开 |
| topK 上限 | 50(平台侧钳制) |
| 超时 | 默认 10s,可配;不重试 |
| 响应体上限 | 建议宿主自限 ≤1MB |

## 7. 与内置 mini KB 的取舍

内置 mini KB 现状:PostgreSQL 全文检索(tsvector)为主,语义层以 `embedding_json`
TEXT 列 + JVM 余弦实现(可选开关,关闭即纯全文行为)。多数场景直接用内置 KB 最省事:
管理面上传文档即可,无需宿主写代码。当**单应用 chunk 数 >5k 且召回不足**(同义改写、
跨语言查询搜不到)时,值得沿 pgvector 路径升级向量索引——在此之前不必引入;若宿主
本就有成熟检索/知识系统,也可不建内置 KB,直接按本篇外接。
