# 最佳实践 · 01 工具授权与确认流

> 平台的授权模型是"**默认安全**":一切工具调用经策略裁决,`DEFAULT` 档 WRITE 类
> 强制用户确认,`ALWAYS_ASK` 档全部确认且授权不可绕过。本篇讲如何把模型用对、用顺。

## 1. 风险分级原则(@IaTool riskLevel / 三方工具同等语义)

| 级别 | 判据 | 例子 | DEFAULT 模式行为 |
| --- | --- | --- | --- |
| `READ` | 无状态变更、无敏感导出 | list_tickets、查余额、搜索 | 自动放行 |
| `WRITE` | 创建/修改/删除/支付/外发 | create_ticket、转账、发邮件 | **用户确认卡 → 确认后执行** |

灰区判据(取严):

- 有副作用哪怕"很小"(改个备注)→ WRITE;
- 读取但数据敏感(全量导出、含他人信息)→ WRITE 或拆细粒度;
- 同一资源的读与写拆成两个工具,而不是一个带 mode 参数的工具(模型选参数
  不如选工具可靠,授权粒度也更清晰)。

## 2. toolExecutionMode 选型

| 模式 | 行为 | 适用 |
| --- | --- | --- |
| `DEFAULT` | READ 放行,WRITE 确认(用户已永久授权的写工具放行) | 绝大多数业务助手 |
| `ALWAYS_ASK` | 所有工具调用均确认,**授权通道关闭** | 强管控(金融/医疗)、审计演练、
**空闲会话压测口径**(挂起等确认,见 k6 idle-sessions) |
| `ALWAYS_ALLOW` / `FULL_ACCESS` | 全部放行(跳过确认)的显式豁免档 | 批量自动化(逐图确认类
"确认踏步机"场景);须由调用方在请求体主动声明,不要作为业务助手的默认 |

注意:确认超时默认 24h,过期自动失效 —— 不要依赖"确认卡挂着随时能点"做业务流程,
关键流程要有超时后的用户引导。

## 3. 工具描述怎么写(决定模型用不用、用得对不对)

- 一句话说清**做什么 + 什么时候用**:"在 ACME 宿主系统中创建一张工单(用户明确
  要求建单/报修时使用)";
- 参数描述写**业务口径**而不是类型复述:优先级 `high/medium/low` 就写全枚举;
- 不要在描述里塞"当用户说 X 时调用我"这类提示词技巧 —— 触发词工程交给系统提示,
  工具描述保持事实性。

## 4. IaActClaims:工具内必须二次鉴权

模型只能"看见"会话上下文里的用户;**工具内部必须以 `IaActClaims`(act token
claims,平台签发、60s 有效)做数据权限过滤**,不要信任模型转述的"用户说他是谁"。

```java
@IaTool(name = "list_tickets", riskLevel = ToolRiskLevel.READ)
public List<Ticket> list(IaActClaims claims) {
    return ticketService.listByOwner(claims.userId());   // 永远以 claims 过滤
}
```

## 5. 确认流的体验设计(宿主前端)

1. 确认卡要**回显全部将执行的参数**(标题/优先级…),用户确认的是完整事实;
2. 挂起期间对话流保持可读(SSE 半开,`WAITING_CONFIRMATION` 是正常态不是错误);
3. 提供明确的"拒绝"路径 —— 拒绝后工具不执行,运行由模型继续组织回复并正常收尾(COMPLETED),审计落 denied;
4. 移动端推送场景:确认卡事件也可经宿主 Webhook 转推,但执行仍需回到平台确认流。

## 6. 审计与追溯

- 每次工具决策(allowed/denied/确认)落审计:`decision` + `decisionSource`
  (admin/user/policy)+ 工具 FQN,**不含任何凭据**;
- 排查"为什么没调工具/为什么弹确认"先查审计,再看会话事件 journal(可回放)。
