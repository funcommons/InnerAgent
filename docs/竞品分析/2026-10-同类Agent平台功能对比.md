## 2. 结论:三条独有护城河 + 三块最大短板

**护城河(三家皆弱、恰为本仓强区)**:

1. **身份信任链**(#1):宿主私钥不出域 + 宿主代用户签发 embed token + act token 受众限定——三家全部是"平台 API key"模型,没有宿主代签信任链;
2. **工具授权确认流**(#2):READ/WRITE 自动分级 + 4 档模式 + 确认卡挂起/恢复——Dify 没有,Langflow/CopilotKit 有 HITL 但分级策略要应用自己拼;
3. **流式可靠性**(#3):Last-Event-ID 断点续传 + 事件重放 + 多实例 outbox——三家的重连语义都是"全量快照兜底"级别。

**短板(按接入方感知排序)**:KB 仅全文检索(无向量语义层)、多模态止于附件(模型侧消费未接线)、Langfuse 型 tracer 导出缺、计费未实现(台账已备)、生态为零。

> 勘误(同日):本表首版对 InnerAgent 列的 5 处误标(RAG/观测/多模态/用量/多 agent 标 ❌)
> 系检索目录错误所致,已按 `inneragent-server` 主源逐一核实修正如上。

## 3. 升级建议

**战略原则**:不追平 Dify 的"平台大而全",把「**宿主嵌入 + 安全授权 + 可靠传输**」做深,
缺的能力优先用"**规范外挂**"补(定义接口让宿主供给),其次才是平台内置。

| 优先级 | 建议 | 理由与做法 |
| --- | --- | --- |
| **P0** | 观测导出开箱化:OTel GenAI span 桥已内建(部署侧 javaagent 激活),补 OTLP exporter 直配项 + Langfuse 适配,并把激活路径写入手册 | 桥已存在,缺的是"开箱";接入方几乎必有既有 tracing 栈,售前验收高频项 |
| **P0** | KB 语义层 + 外部知识库:给 mini KB 加可选 pgvector 语义检索(全文为降级),同时定义《宿主检索工具/外部知识库 API 规范》对标 Dify External Knowledge API 的反向定位 | 引用留痕/溯源管道已备,补语义层与"知识在外"的接入规范即成完整 RAG 故事,零自建重资产 |
| **P0** | 多模态闭环:附件管道已有,补模型侧 vision 消费(image_url 接线)+ sdk-js 附件 UI | 工单截图等宿主场景高频;只差最后一公里 |
| **P1** | per-app 用量统计(运行数/工具调用/token) | 台账(`ModelCallUsageLedger`)已备;补聚合查询 API 与管理面大盘,计费继续留端口 |
| **P1** | **AG-UI 兼容层**:server SSE 事件 → AG-UI 事件适配器 | AG-UI 已成行业标准(20+ 框架桥);适配后本仓前端直接接入 CopilotKit 生态,而 Last-Event-ID+重放反成为 AG-UI 生态独有传输增强——把短板#16 生态用一条适配器换回来 |
| **P1** | "定时/事件驱动运行"以**接入规范**交付(宿主调度调 POST /runs),不建平台内 cron | 程序化触发已存在,平台建 cron 属重复建设;写清模式即可 |
| **P2** | 多 agent 协作(agentType 间委托/subagent) | Dify/Langflow 已标配;中台场景先支持"主 agent 委托专家 agentType"即可 |
| **P2** | 内置轻量知识库(仅在 P0 外挂路线被证明不够时启动) | 避免与 Dify 正面竞争的自建重资产 |
| **不做** | 可视化 canvas 编排、Marketplace 生态、SaaS 计费体系 | 与定位冲突;编排留在代码/DSL,生态借 AG-UI 适配层 |

**一句话**:本仓用 3 条护城河对 3 家头部互有攻守;升级主轴是「**把缺的能力规范化为宿主外挂、
把独有能力标准化为行业协议(AG-UI 适配)**」,而非复制 Dify。

## 附:三竞品各自最强三点(调研原话摘录)

- **Dify**:① workflow+chatflow 双可视化编排与嵌套子图;② RAG 管道+外部知识库开放 API;③ Marketplace 生态与 MCP 双向原生。
- **Langflow**:① 可视化+MCP 双向生态(每 project 即 MCP server);② 工具级 HITL 审批(checkpoint 暂停/分支恢复);③ 九类向量库+七种 tracer。
- **CopilotKit**:① AG-UI 协议+约 20 框架官方桥接(Google/AWS/Microsoft 采用);② HITL 双模式+前端工具审批 UI 打磨最深;③ 同一套代码云/自托管,持久 threads+用户记忆开箱。
